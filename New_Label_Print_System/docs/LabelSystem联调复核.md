## 首打、补打和恢复的补充验收

| 场景 | 检查层次 | 本轮结论 |
| --- | --- | --- |
| 首打/补打创建请求响应丢失 | React durable/retryCreation；Flask实际transport边界 | 保留原clientRequestId和请求体，重试原创建；不产生替代身份；SQLite不建另一套正式账 |
| 助手已提交、浏览器丢响应 | React调用顺序；Go持久账本恢复 | 首打和补打均GET原job/attempt；模拟驱动调用1次，不重新POST发送 |
| 服务端登记成功但回执响应又丢失 | React模拟服务端响应丢失 | 重交同一签名回执，不新建任务/授权，不再发送；实际SQL幂等仍依赖后端约束及后续全过程验收 |
| 三表登记失败与多次恢复 | React恢复路径；Flaskretry-sync错误透传；共享API规则测试 | 只调用同job的retry-sync，保留错误和待登记状态，不调用助手；本轮未向实际三表注入故障 |
| UNKNOWN、助手404或原证据损坏 | React及Go模拟 | 不认为未发送，不自动重发；损坏账本/残留锁连续重试仍不触发模拟驱动 |
| 两个助手实例并发同attempt | Go真实文件账本/锁、模拟驱动 | 第二实例读到原UNKNOWN，完成后读原submitted；模拟驱动总计1次 |
| 关闭发送后恢复 | Go模拟及真实下载配置 | 新发送409，GET原签名回执仍可用 |
| 权限即时撤销 | Flask逐请求权限/transport边界 | 首打、补打、回执、同步重试、授权分别403且未调用上游 |
