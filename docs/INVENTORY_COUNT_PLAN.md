# 盘点单实施方案

方案日期：2026-11-04。状态：供业务确认的实施建议，尚未开发、迁移或放行写入。基线与已完成范围见[项目当前状态](PROJECT_STATUS.md)。

## 1. 现有实现与缺口

- H5 `business-document-config.ts` 中盘点的 `sourceTypes=[]`；Business API `DocumentPrepareService` 中 `SupportsSource=false`，携带来源时返回 `SOURCE_NOT_SUPPORTED`。
- 当前无原单路径会新建U8盘点单，`DocumentGatewayRequestBuilder` 按每张标签映射 `icvquantity=InventoryQtySnapshot`、`icvcquantity=RequestedQty`；尚未处理多标签汇总到既有盘点行的规则。
- U8真实表/字段已有只读合同：`CheckVouch / CheckVouchs`，单号 `cCVCode`，表体 `autoID`，账面数量 `iCVQuantity`，实盘数量 `iCVCQuantity`，物料 `cInvCode`，批号 `cCVBatch`，货位 `cPosition`。单位/自由项/行版本必须按真实合同再核验，不能只按料号关联。
- Gateway当前盘点能力包含query/create/verify/unverify，`update=false`；运行时没有可直接放行的盘点实盘回填链。不能仅增加下拉框或把全局update开关改为true。
- `TraceBackSnapshotService` 的提交复核白名单、`TraceBackSyncPlanner` 的来源事件都没有盘点。带旧表游标的标签可能在ERP新增成功后因不支持同步进入待核对；如果未同步旧表，后续扫码也可能把本地实盘余额刷新回旧余额。
- `U8_COM_Code` 有参考性的盘点明细修改流程，采用Load原XML、只改指定行、组件Update并回读；仅作为组件/字段线索，不复制其业务实现或数据库连接。
- 离线能力目前仅有部分基础：已完成草稿使用IndexedDB，编辑中跨子页状态使用sessionStorage，扫码每次仍调用库存查询API，没有盘点离线标签包或逐次采集日志。`offlineSessionHours=24`只是客户端配置字段，当前会话读取仍受实际expiresAt限制，不能据此声称已有24小时离线授权。
- 当前APK包装页仍加载远程H5，并在地址不可达时显示断网遮罩；没有经过验收的离线业务资源包。必须同时处理本地数据、页面资源和扫码桥，不能以网页缓存或已有草稿代替离线扫码/重启恢复能力。

## 2. 建议的首期流程

建议以“U8先生成盘点单，PDA选择原单并回填实盘”为首期主流程。原单是待处理的盘点单本身，不是用来再新建另一张盘点单的上游订单。

```text
U8生成未审核盘点单
  → PDA选择一张盘点单及本次盘点行
  → 联网冻结盘点范围，下载完整任务包并绑定PDA
  → 在线或离线扫描/登记范围内标签及实盘数量
  → 联网同步采集记录，实时复核范围、原单与标签
  → 汇总到原单行，核对未盘项、差异及版本
  → 上传回填同一张U8盘点单，回读确认
  → 审核确认后按每张标签登记盘点差异
  → 新旧余额一致，释放对应标签占用
```

首期一份PDA任务只关联一张U8盘点单；不跨账套、不跨原单合并。原单已审核、已记账、已关闭或不处于允许修改状态时拒绝回填，具体状态字段在888只读核查后固化。来源列表与采购/生产源单不同，查询未审核可盘点单，不能复用“只显示已审核订单”的过滤。

盘点页面建议保留“选择盘点单”“盘点明细”“未盘 / 已盘”“账面 / 实盘 / 差异”等简短文案。表头仓库、日期、部门等由原单带入；数量及权限由后端复核。原单之外的标签不自动新增到原单中。

当前无原单新建代码先保留兼容但不作为首期开放路径；待原单模式验收后，再单独设计无原单的新建范围和U8账面基数查询，不能继续直接将一张标签的余额充当U8整行账面。

## 3. 原单行、标签与数量口径

原单行用 `U8盘点单ID + CheckVouchs.autoID` 标识；料号、批号、仓库、货位、库存单位及必要自由项共同决定匹配身份。相同身份有多个原单行时要求明确选择或待核对，不默认匹配第一行。

U8账面数取原单当前 `iCVQuantity`，保留为原单冻结基数。标签账面数取完整Code的TraceBack余额。二者分开保存、展示和校验，均不能取Code中打印数量替代。

| 数据 | 计算方式 / 规则 |
| --- | --- |
| 每张标签差异 | 本次确认实盘数 − 冻结并复核通过的标签余额 |
| 原单行实盘数 | 完整盘点范围内、明确完成确认的全部标签实盘数之和 |
| 原单行差异 | 该行实盘数 − U8原单账面数 |
| 正常闭环校验 | 范围内标签账面合计 = U8原单账面；标签差异合计 = 原单行差异 |

例如原单账面100，同位置两张标签60和40，实盘55和42，则回填原单实盘97；旧码分别追加−5和+2。不能把两张标签建成两张新的盘点单，也不能每次扫码都覆盖整行实盘。

完成行前必须明确盘点范围：按原单行身份取得应盘标签清单，并与U8原单账面核对。只扫描其中一张不能认定整行已经盘完。未扫描不等于数量0；只有明确确认“未找到，实盘0”的标签才记零。同一盘点任务的完整Code再次扫码必须拒绝，显示“标签已扫描”并触发警示/失败反馈；不打开编辑、不新增明细、不覆盖实盘或累计数量。需要改数时，从已有明细主动进入修改，替换该标签实盘数并记录修订。

若旧三表无法可靠枚举范围，或存在无标签库存、跨库存身份合并、缺自由项、重复/异常标签、TraceBack账面合计与U8账面不符，首期阻止该行完成并列为待核对，不把差异自动摊给其他标签。盘盈、盘亏、零差异和实盘0均应支持；托盘、单位换算、无码实物新建标签、批次/位置纠正不在首期。

## 4. 生效时点与外部变动

建议将“保存实盘结果”和“盘点差异生效”分成两个阶段：回填未审核单时仅保存盘点任务、冻结快照及U8结果，不立即修改标签余额；U8审核回查确认后才落标签差异。这样未审核的可修改实盘不会提前改变可用库存。该时点属于本方案建议，需业务确认，并在888验证U8审核/记账及自动生成盘盈盘亏单的实际行为后最终固化。

盘点期间对选定范围建立业务占用。旧客户端不遵守本地锁，因此在提交、审核确认及写旧表前都要重新查询原单版本和标签最新流水、余额、位置。存在外部变化时停止完成，保留草稿并要求重新盘点/核对；不能直接把最新余额替换成旧实盘数，也不能无提示改变差异基数。

同一来源盘点单/行的任务需有排他占用，防止多个PDA覆盖；已回填但未生效任务保留范围锁，支持同一任务继续编辑或受控撤销，完成后不因普通编辑再次落差异。持锁不禁止其他客户端直接改U8，因此U8组件时间戳仍是最后一道并发校验。

审核针对整张U8盘点单，不能只因本次选中几行完成就自动审核整单。自动审核前必须确认原单所有盘点行均有完整完成证据；其他行若由U8人工盘点，也需可核查的确认记录。尚有未盘行则仅保存本次实盘，不触发整单审核；首期优先整单单任务，跨设备分工后置。

回填、待审核、差异同步和完成需要独立状态，不能把原单回填成功就展示为库存盘点已完成。若用户直接在U8审核，需由按来源单的状态核查/恢复流程识别后继续原事件，而不是另建一张单。首期禁止由本系统对已生效盘点直接弃审；后续冲销必须先核对关联单及后续库存动作，再以独立反向事件处理。

## 5. Gateway与Business API

以下为拟新增接口，不是现有可调用合同，最终路径在实现时与已有路由统一：

| 层 | 拟接口 | 职责 |
| --- | --- | --- |
| Gateway | `GET /api/v1/inventory-counts` | 固定表、参数化搜索可修改盘点单，分页并返回单号/仓库/日期/状态/版本 |
| Gateway | `GET /api/v1/inventory-counts/{id}` | 表头、稳定行ID、原单账面/实盘、库存身份、行/单据版本及状态 |
| Gateway | `POST /api/v1/inventory-counts/{id}/actual-quantities` | 原单版本+稳定行ID+绝对实盘数；Load原XML、仅修改允许的实盘字段、保留系统字段/未改行/原生时间戳、调用组件Update及回读 |
| Gateway | `POST /api/v1/traceback/labels/snapshots/by-inventory-scope` | 受限、完整分页的应盘标签范围；沿用异常规则，限制单行范围，评估执行计划；不能用最多100个Code的接口假装完整枚举 |
| Business API | `GET /api/v1/inventory-counts` 及 `GET /{id}` | 身份/权限校验后代理原单读取，返回与标签任务关联的信息 |
| Business API | `POST /api/v1/inventory-counts/{id}/prepare` | 建立或恢复盘点任务，冻结范围、标签和原单版本，并建立任务占用 |
| Business API | `POST /api/v1/inventory-counts/{id}/submit` | 重新复核、汇总并回填原单，使用原请求号，保存回读结果及待审核状态 |
| Business API | `POST /api/v1/inventory-counts/{id}/finalize` | 查询原单审核状态，按已确认时点幂等产生盘点差异及旧表同步任务 |
| Business API | `GET /api/v1/inventory-count-sessions/{sessionId}/offline-package` | 返回prepare阶段形成的不可变任务包、版本、完整性摘要及限定范围；未完整就绪不能标为可离线 |
| Business API | `POST /api/v1/inventory-count-sessions/{sessionId}/observations/batches` | 按原采集事件ID和任务分配版本幂等接收实盘记录，只同步草稿，不改U8或标签余额 |
| Business API | `POST /api/v1/inventory-count-sessions/{sessionId}/validate` | 联网后核对原单、完整范围及每张标签版本/余额/位置，返回冲突；通过后才进入submit |

修改盘点实盘使用窄字段专用路径；不开放其他单据通用PATCH或delete，不允许客户端提交表名、SQL、账面数或任意表头/表体字段。Gateway必须先核对真实USERPCO Update签名、装载XML、行时间戳及差额派生行为，不能照搬Insert参数或直接SQL更新 `CheckVouchs`。

增加 `INVENTORY_COUNT_GAIN / INVENTORY_COUNT_LOSS` 事件角色，数量是有符号差异，旧Code及位置保持不变；零差异只记完成审计，不额外写三表数量流水。新事件的Order类型、Goods JSON和字段白名单先在888核对，不能套用材料出库或移动类型。

稳定事件键绑定命名空间/环境/账套/原单ID/本地任务及生效版本/标签ID；相同业务重试使用原键。差异事件需要标签最新版本、余额及来源盘点证据，禁止客户端任意调整库存。旧三表使用既有事务和确定性UUID，同步后核对新旧余额。

## 6. 数据库迁移建议

候选迁移018，新增脚本名称建议 `053_inventory_count_sessions.sql`，实施前核对编号是否仍可用；本轮不创建或执行SQL。复用 `business_operation`、`business_operation_line`、`inventory_flow`、`traceback_sync_task` 和现有用户/权限。

建议增加盘点专用session/行/标签范围关联，保存：环境与账套、U8单据ID/单号、原单版本和行ID、任务状态、范围完整性标记、U8原单账面快照、标签余额/最新流水/位置快照、实盘数、明确零数或已盘标记、执行人、提交请求号、回填/审核/同步完成时间及错误。必要的字段可以落在专用表，避免给所有业务明细塞入盘点专有状态。

离线任务另保存设备绑定、分配代次、不可变任务包版本/条数/哈希及采集许可到期时间；采集记录保存eventId、设备本地序号、标签完整Code、实盘值/状态及修订号。服务端以任务+eventId去重、以任务+标签约束当前实盘，不把重复上传批次当作重复扫描累计。客户端时间只用于展示/审计，不决定库存版本或最后写入顺序。

关键约束：一个原单行同一时点只有一个活跃任务；每个任务每张标签唯一；同一生效事件唯一；未盘状态与实盘0可区分；已生效实盘快照不可覆盖。请求号和载荷摘要沿用既有幂等要求，错误/重试次数/完成时间复用同步任务字段，不另建第二套同步队列。

## 7. 失败恢复与验收

- 写U8前失败：不落盘点数量流水；已保存任务可修正后继续。
- U8回填成功但响应丢失：先按同一任务、原单ID、稳定行ID及目标实盘数回读，不新建U8单据、不追加增量。
- U8审核成功但本地结果未知：保留任务/锁，恢复时先回读状态，再原事件幂等完成。
- 本地保存差异及同步任务必须原子提交；旧三表失败或丢响应时只补原任务，禁止重新回填、审核或重复生成盘盈盘亏单。多标签部分同步要逐标签保留完成证据和未决占用。

888必须验证：单/多标签汇总，盘盈/盘亏/实盘0/零差异，未盘项不能默认0，同一身份多原单行，原单外标签，异常标签，U8与TraceBack账面不符，双PDA并发，外部改原单/改标签，已审核/已记账拒改，回填/审核/本地提交/旧表失败与丢响应恢复，以及审核关联单行为。

自动测试覆盖状态转换、绝对数量回填、范围完整性、字段保留、并发版本、异常拒写和重复事件；真实888集成测试分别比较U8原单及其关联结果、新表流水和旧三表，不以单元测试替代。首期不写008，也不以本方案表示盘点已可上传。

离线验收必须补充：下载中断/缺页/摘要错误不可离线启用；断网连续扫描、同码重复拒绝并警示、实盘编辑及显式0；每次本地保存后杀进程/重启恢复；存储满或禁用不得误报保存成功；无网冷启动加载本地匹配版本；上传丢响应/重复批次/乱序旧修订；账号停用或会话到期保留数据并拒绝未授权提交；任务转交后旧PDA不能覆盖；离线期间旧系统改余额/位置、原单被修改/审核、新增应盘标签或原范围标签移出时保留采集并进入冲突。

重复扫码专项验收覆盖在线、离线、快速连续输入、保存尚未完成、待核验未知码及设备重启后的再次扫码。每种情况必须只有一条标签采集记录，原实盘/已盘数/汇总不变，重复输入走警示而非成功声音；从明细修改数量仍可正常保存。上传原事件的幂等重试属于网络恢复，不触发用户重复扫码警告。

## 8. 分阶段交付

1. 只读核查888真实盘点单、Update合同、状态及库存身份；固化读取合同，先让PDA能选择原单、查看范围和录入草稿，预留离线包版本及设备任务身份。
2. 迁移018、范围/标签占用、完整任务下载、逐次IndexedDB持久化及离线资源包；完成断网扫描和杀进程/冷启动恢复，再接联网同步、冲突复核、原单行汇总及实盘回填。采集同步/保存均不改变标签余额。
3. 审核生效、差异事件、恢复和三方对账；按上述矩阵完成888验收。
4. 经业务确认后再安排008单独发布；无原单新建、无码盘盈和复杂跨设备分工后置。

实施前需确认的业务选择：采用U8原单回填作为首期；标签差异按审核确认后生效。若实际要求是PDA直接生成新盘点单或保存立即生效，应先修订本方案，仍需保留范围完整性与差异一致性校验。

## 9. 离线扫码与恢复方案（11月4日补充，尚未实现）

离线扫码属于首期盘点采集能力；离线修改U8、修改标签余额或登记旧三表仍不开放。两者不能合并成“全部离线后置”。

### 9.1 出发前联网下载完整任务

先在线登录，选择原单，由服务器创建盘点任务/范围占用，并绑定账号和一台PDA。下载包至少包括：服务器业务命名空间、环境、账套及库/年度标识、任务和分配代次、原单ID/单号/行ID及版本、盘点范围完整清单、完整Code到标签/原单行的映射、每码余额/最新TraceBack流水/身份/位置、必要物料名称和单位/批次规则、任务包schema和H5兼容版本、条数/哈希，以及服务器签名、限定任务范围和到期时间的采集许可。本机只保存验签所需公钥，不持有服务端签名密钥；联网写入仍重新认证和复核，不能只信任本地许可或采集内容。

分页下载使用同一不可变包版本；全部页/条数/摘要匹配后，在本地事务中切换为可离线任务。中途断网、包过期、缺页或空间不足时保留原可用包，不把半包标记为“下载完成”。不全库下载物料或追溯历史，每个任务只带应盘范围；准备范围的SQL性能先在888验证。

任务包是盘点基线，不是实时可用库存凭据。范围占用优先在下载前建立；多设备分工先不开放。同一任务重下载/重试保持同一身份，不能因为包传输失败新建任务或重复占用。

### 9.2 离线采集逐次持久化

离线扫码直接用完整Code命中已下载的应盘标签，显示包中的名称、批号、位置和“下载时账面”，由用户填写或确认实盘。若默认带入账面量，也必须经确认才标为已盘。同一任务重复扫完整Code时拒绝接收，显示“标签已扫描”并播放警示声，不自动打开已有明细或改变数据；显式修改从明细列表进入并产生新修订，实盘0和未盘保持可区分。

去重范围为任务内完整Code，在线/离线规则相同，覆盖已盘、已暂存待核验及正在处理的条码。快速输入使用处理中占位及本地唯一约束，防止第一个保存尚未完成时第二次也被接收；首次保存失败则解除相应处理中占位，允许重新扫描。重启后从持久记录恢复去重，不只靠页面内存或800ms广播去抖。警示走现有失败反馈通道，尊重用户已选择的反馈模式；关闭声音时仍显示文字且拒绝重复。

未命中任务包的条码允许保存原码及用户实盘输入，状态为“待核验”，不猜料号/位置、不读Code数量作余额、不计入已完成原单行；联网查询后再决定归属或要求重新下载。无效和异常条码保留可追查原始采集记录，不自动当成新标签或盘盈。

每次扫码确认、数量修改和显式盘零，都在同一IndexedDB事务写入采集事件、当前实盘投影及待同步标记；事务完成后才给出“已保存”反馈。扫描器收到码的声音不能当作落盘成功。存储错误提示“未保存”，停止给出成功反馈并要求处理，不能只把数据留在Vue内存/sessionStorage。

本地数据按服务器命名空间+环境+账套/数据库+账号+设备+任务隔离；不能只沿用当前按environment命名的草稿库来区分008/888。使用任务包schema和版本记录恢复进度，重启后重建当前投影；“本地已采集”“已同步”“U8已回填”“盘点完成”分开表示。

### 9.3 页面资源和离线重启

持续打开的页面断网后不刷新iframe、不强制跳登录页，也不因远程H5健康探测失败用遮罩挡住已准备的盘点任务。保存输入并保持扫码桥处理；只有无法装载业务页面时才进入启动故障提示。

仅靠当前远程H5和WebView缓存，不能承诺断网重启后继续盘点。建议为APK增加可核验的版本化本地H5资源包：下载并校验清单/哈希、入口、脚本、样式及字体后原子切换，始终保留上一可用包；离线从本地固定来源装载匹配版本，桥接口不依赖远程页面在线。包内不含密码、API Key或数据库配置。

本地业务页面采用稳定来源/存储身份，不因版本路径变化丢失IndexedDB；由现有远程来源切换本地来源时必须在线显式迁移或先清空待同步队列，不能直接改iframe地址后假定旧草稿仍可见。任务未同步时不强制更新H5或数据库schema。该能力需要APK桥和H5共同开发，验收覆盖APK杀进程、设备重启、无网启动和恢复扫描，不以已有品牌启动动画作为替代。

首期“离线扫码完成”必须同时满足已打开页面断网续扫和已下载任务断网冷启动；在本地资源能力未验收前，只能标注“页面保持打开可继续”，不能宣布完整离线可用。未登录过或从未下载任务的设备仍需先联网。

### 9.4 联网同步与冲突处理

恢复网络后，先校验原服务器/账套绑定及当前账号、权限、任务归属和分配代次；API令牌失效则重新登录同一账号，保留所有未同步数据。离线采集许可与在线Bearer分开管理，不能拿过期Bearer执行U8写入；许可只允许已下载范围内采集。

采集日志按稳定eventId和单设备本地序号分批同步；每批持久化原请求号和载荷，丢响应重试原批次。服务器确认已接收的事件才能标已同步；后到达的旧修订不得覆盖新实盘。草稿自动同步不等于自动回填/审核，正式提交仍遵循用户上传操作和已配置的自动上传/审核策略，并先通过实时复核。

完成前必须重新核对：U8原单当前状态/版本/账面、任务范围是否完整、每张标签最新流水/余额/位置，以及下载后新增或移出范围的标签。仅比较已扫码Code不能发现新标签进入。任何实质变化都列为冲突，保留已采实盘，让用户确认重新盘点或重建范围；不静默用旧实盘覆盖新库存，也不自行按变化量补算。

若扫码前后已发生无法判断的出入库，当前TraceBack快照不能证明盘点瞬间库存，因此不能仅因用户确认一次就绕过复核。需要明确停作业窗口或重新盘点；本地占用只能约束新系统，旧客户端仍需现场协调。

### 9.5 到期、转交与本地数据保留

建议初始离线采集许可按一个班次、最长8小时配置，具体时长待业务确认；不能直接使用现有offlineSessionHours=24视为既定策略。到期停止接受新采集，允许查看已保存结果；联网重新认证和复核后续用，不清理待同步任务。设备时钟回拨/时间依据异常时要求联网校准，不将客户端时间当服务端授权证据。

许可到期或心跳消失不自动释放盘点业务占用。取消、转交或管理员恢复需要服务器明确操作并递增分配代次；旧PDA恢复后不能覆盖接收设备的数据，可保留旧采集用于人工核对。清缓存、退出或切换账号时提示未同步数据，保留受账号隔离的任务，不做静默清除；卸载/清除系统应用数据仍可能丢失本机未同步记录，现场交接需先确认已同步。
